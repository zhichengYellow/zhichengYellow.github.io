不优化也是一种优化：Nexus LLM Gateway 如何用真实数据降低 Token 消耗

不优化也是一种优化：Nexus LLM Gateway 如何用真实数据降低 Token 消耗

LLM 成本优化最容易犯两个错误：把统一 API 当作网关的全部价值，或把 token 变小都记作节省。

Nexus 是开源的 BYOK、OpenAI-compatible LLM Gateway，支持 7 家 Provider。核心是让优化请求可测量、可解释、可复现：缓存、压缩、去重、路由各自减少了什么，优化又付出了多少代价。

本文只讨论 v2.3.0 在 2026 年 8 月 10 日、DeepSeek 线上网关、缓存已预热条件下的 benchmark。所有百分比和延迟均来自仓库的 benchmark/benchmark-report.md 与 benchmark/results/；这不是对任意模型、任意流量分布的通用承诺。

问题：为什么“省了多少”比“接了多少模型”更难

实现缓存、压缩、路由和去重不难，难的是让它们在同一请求上正确协作。缓存命中后不能再把压缩收益重复计入；SingleFlight 也不能把同一份上游成本记十次。被 max_tokens 截断的响应即使命中缓存，也没有节省意义。

因此 Nexus 的设计起点不是先宣称节省比例，而是先定义证据：每个请求必须能回答“为什么省了”“省的是哪一部分”“是实际发生还是估算”“优化代价是多少”。

设计：从请求路径到可解释账本

Nexus 的优化链路是：精确缓存和单租户语义缓存，随后上下文压缩、SingleFlight 请求去重、智能路由，最后由 Savings Engine 和分阶段计时记录结果。

这里最重要的不是层数，而是两个约束。

第一，Savings Engine 使用互斥归因。每次节省只归到一个原因：CACHE、COMPRESSION、ROUTING、REWRITE 或 DEDUP。这避免缓存和压缩同时宣称同一段 token 的收益，也让报表能按机制拆解。

第二，ACTUAL、ESTIMATED 与 PROJECTED 严格分离。缓存命中、实际 token usage 和真实价格表能得到的，才属于 ACTUAL；基于未发生调用或模型估算得到的，只能是 ESTIMATED 或 PROJECTED。页面上把三者混成一个“已省成本”数字，短期好看，长期会失去可信度。

最终每次请求记录 explainability：命中何种缓存、压缩前后 token、是否复用 in-flight 请求、路由结果、归因类型和分阶段耗时。总节省也不是只看 Gross Saving，而是：

Optimization Cost 包括为了缓存判定、压缩、路由等额外发生的开销。只统计“少发给上游多少”，却忽略网关为了做判断而付出的代价，会高估系统价值。

数据：不同 workload 受益于不同机制

基线是“网关 fast 档 + 关闭缓存”，用于逼近直连调用而不是制造一个性能很差的参照组。优化组使用线上网关且缓存已预热，这对应真实使用中已经产生过相同或相近请求的场景。

这个表最值得关注的不是 100%，而是最后一行。短代码请求或短 prompt 没有足够冗余时，网关没有为了制造“节省”数字去压缩、重写或额外调用判断模型。结果是约 0% 的 token reduction。它并不漂亮，但它是正确结果：一个优化系统应当识别没有收益的请求，并让它原样通过。

重复问题和中文 workload 的 100% reduction 来自预热缓存直接返回，并不表示模型生成本身免费。Document QA、Long Context 和 Conversation 分别受冗余、历史语境和缓存机会影响，说明不存在单一的“网关节省率”。

缓存：命中率之外，正确性才是硬约束

Nexus 同时使用精确缓存和语义缓存。语义缓存的价值在于捕捉不同措辞下的相近问题，但它的风险也最大：如果 key 只包含 prompt 文本，而没有租户边界，就可能把 A 用户的答案返回给 B 用户。

这不是一般命中不准，而是跨租户串读漏洞。缓存 key 必须包含 tenantId，语义检索和精确命中都在单租户范围内完成。

另一个真实坑是被截断的响应。上游的 max_tokens 过小时，响应会因 length 截断。这样的结果不能写入缓存；否则后续命中会稳定返回一段看似成功、实际不完整的答案。网关需要把“响应可缓存”作为显式判断，而不是只要 HTTP 成功就写入。

这也是“缓存合理拒绝缓存”的含义。少一次命中可能减少纸面节省，但能避免把错误答案规模化扩散。

去重、路由与归因：不要让一笔账出现两次

SingleFlight 处理的是并发重复请求：同一个 key 已经在请求上游时，后来的相同请求等待第一个结果，而不是再次发起调用。这降低的是并发峰值下的重复工作，与“历史缓存命中”不同，因此 Savings Engine 将它作为 DEDUP 单独归因。

智能路由则在真实注册表的 7 家 Provider 候选中选择合适路径。它不是默认选择最便宜模型，而是将任务类型、模型可用性和成本约束纳入选择；没有满足约束的候选时，系统必须让降级状态可见，而不是静默突破预算。

两者都不能和缓存、压缩重复计数。一个合理的账本逻辑是：先确定请求是否已经被 cache 或 dedup 消解；只有仍需生成的请求，才比较压缩或路由带来的差异；最后再区分 ACTUAL 与 ESTIMATED。这样即使多个优化条件同时成立，用户也能知道最终数字来自哪里。

互斥归因不会让总数更高，恰恰相反，它阻止报表重复加总。这是成本观测系统应接受的保守性。

Optimization Overhead：优化本身也要被测量

缓存查找、语义判定、压缩、路由都会增加额外工作。即使上游 token 降低了，如果这些动作的延迟和成本被忽略，系统可能只是把账单从 Provider 转移到了网关。

Nexus 对 pipeline 分阶段计时，记录 Optimization Overhead，并把它放入 Net Saving 计算。这个设计有两个直接好处：一是能定位某个优化阶段是否变慢，二是能避免把“低 token”误判为“低总成本”。对 Coding / Short Prompt 这类约 0% reduction 的 workload，正因为没有明显压缩空间，避免强行优化也意味着避免不必要 overhead。

展望：把“更省”变成可证伪的工程结论

一个可信的 AI Gateway 不应承诺一个脱离条件的节省百分比。它应该让开发者看到：本次请求是否命中缓存，为什么没有命中，压缩减少了多少输入，是否由 SingleFlight 复用，路由是否改变，优化开销多大，以及最终是 ACTUAL、ESTIMATED 还是 PROJECTED。

下一步应扩大可观测性、完善隔离和缓存策略，并用更多 workload 验证 Net Saving。短 prompt 的约 0% 结果说明，网关也必须知道什么时候不该出手。
